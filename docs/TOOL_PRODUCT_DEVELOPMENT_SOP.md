# 工具产品开发 SOP

适用于个人工具、桌面工具和 AI 工具的产品设计与开发。目的不是增加流程，而是减少目标漂移、过早开发和重复返工。

## 一、基本原则

1. 一个阶段只解决一个核心问题。
2. 产品范围未冻结，不进入原型设计。
3. 原型未确认，不修改正式代码。
4. 只有一份正式设计稿，截图只用于反馈问题。
5. 新想法默认进入后续需求，不直接打断当前开发。
6. 所有“效果更好”必须有固定样本和可比较的结果。

## 二、标准流程

### 1. 定义问题

开始前必须回答：

- 用户真正要完成什么？
- 当前最主要的问题是什么？
- 为什么现在必须解决？
- 最终结果如何判断成功？

输出一句话目标：

> 为【目标用户】解决【核心问题】，使其能够【可验证结果】。

未能写出一句话目标时，不进入下一阶段。

### 2. 冻结本阶段范围

建立本阶段任务卡：

```text
阶段目标：
必须完成：
明确不做：
完成标准：
唯一设计稿：
验证方法：
```

范围确认后，新需求按照“变更处理”执行，不能直接加入当前任务。

### 3. 完成产品设计

先确定页面和功能职责，再处理视觉样式。

必须覆盖：

- 主流程
- 空状态
- 有数据状态
- 处理中状态
- 成功状态
- 失败状态
- 批量处理状态
- 中断和恢复方式

产品设计完成后，先确认信息是否完整，再进入视觉设计。

### 4. 冻结设计稿

指定一份文件作为唯一设计标准，记录：

- 页面尺寸与适配范围
- 字体、字号、字重和行高
- 图标库及图标名称
- 颜色、圆角、边框和阴影
- 主要间距和控件高度
- 交互状态与页面跳转

设计冻结后才能开始编码。设计需要变化时，先更新设计稿，再修改代码。

### 5. 实施开发

开发顺序：

1. 数据和状态结构
2. 主流程功能
3. 异常与恢复
4. 页面结构
5. 视觉还原
6. 自动化保护

开发过程中不得自行增加设计稿以外的功能。发现产品缺口时，暂停对应部分并回到产品设计阶段。

### 6. 验收

功能验收：

- 主流程可以完整执行
- 批量任务互不干扰
- 失败不会破坏已完成结果
- 中断后能够继续或重新开始
- 结果可以找到、查看和导出
- 错误信息能够指导下一步操作

UI 验收：

- 页面结构与正式设计稿一致
- 字体、字重、行高一致
- 图标来源、尺寸和线宽一致
- 间距、控件高度、圆角和颜色一致
- 空、处理中、失败、完成状态均已检查
- 不使用“相似图标”或临时 CSS 图形代替正式资源

质量验收：

- 使用固定测试样本
- 保存修改前后的结果
- 自动化测试通过
- 记录仍未解决的问题

验收未通过，只修复验收问题，不在此阶段扩展功能。

### 7. 结束与进入下一阶段

每次交付必须记录：

```text
本次完成：
验证结果：
已知限制：
没有完成：
后续需求：
下一阶段目标：
```

完成记录后，本阶段关闭。下一阶段重新创建任务卡。

## 三、需求变更处理

出现新需求时，只做一次判断：

- 不影响当前核心流程：加入后续需求，继续当前任务。
- 直接阻塞当前核心流程：暂停开发，重新确认范围和完成标准。

任何范围变化都必须同步修改任务卡。不能只在聊天中口头改变范围。

## 四、AI 功能专项规则

AI 功能不能用“感觉更好”验收。必须建立固定验证集，至少覆盖：

- 常规内容
- 中英文混合
- 人名、公司名和产品名
- 专业术语和缩写
- 低音质或口音
- 长内容和重复内容

至少记录：

- 原始错误数
- 修复正确数
- 未修复错误数
- 新增错误数
- 影响理解的严重错误数

没有验证结果，不更换模型、不扩大提示词，也不宣称准确率提升。

## 五、协作约定

每次开始任务时，执行者必须先说明：

1. 当前目标
2. 本次要完成的内容
3. 本次明确不做的内容
4. 完成后的验证方式

执行过程中只汇报重要变化。需要决策时，只提出会影响范围或结果的问题。

每次结束时只汇报：完成内容、验证结果、已知限制和下一步。

## 六、开始开发前检查

- [ ] 一句话目标已经确认
- [ ] 必须完成和明确不做已经写清楚
- [ ] 完成标准可以验证
- [ ] 页面职责已经确定
- [ ] 所有必要状态已经设计
- [ ] 唯一正式设计稿已经指定
- [ ] 测试样本或验收数据已经准备
- [ ] 当前没有未确认的阻塞决策

任何一项未完成，都不进入正式编码。
